    - /Odometry [nav_msgs/msg/Odometry]

  （1）Header

  ​ std_msgs/Header header：包含消息的元数据

  ​ builtin_interfaces/Time stamp：消息的时间戳

  ​ int32 sec：秒数

  ​ uint32 nanosec：纳秒数

  ​ string frame_id：标识父坐标系的帧ID

  （2）Child Frame ID

  ​ string child_frame_id：指定这个位置和速度估计所使用的坐标系，通常是机器人本体坐标系

  （3）Pose

  ​ geometry_msgs/PoseWithCovariance pose：标识机器人在指定位置和姿态

  ​ Pose pose：包含位置和方向

  ​ Point position：机器人的位置

  ​ float64 x，float64 y，floatz

  ​ Quaternion orientation：机器人方向，使用四元数表示

  ​ float64 x，float64 y，float64 z，float64 w

  ​ float64[36] covariance：位置和姿态的协方差矩阵，表示对这些估计的信息

  （4）Twist

  ​ geometry_msgs/TwistWithCovariance twist：标识相对于child_frame_id的线性和角速度估计

  ​ Twist twist：包含线性和角速度

  ​ Vector3 linear：线性速度

  ​ float64 x，float64 y，float64 z

  ​ Vector3 angular：角速度

  ​ float64 x，float64 y，float64 z

- /livox/imu[sensor_msgs/msg/Imu]

  （1）Header

  ​ std_msgs/Header header：包含消息的元数据

  ​ builtin_interfaces/Time stamp：消息的时间戳

  ​ int32 sec，uint32 nanosec

  ​ string frame_id：指定坐标系的帧ID，通常是IMU的参考框架

  （2）Orientation

  ​ geometry_msgs/Quaternion orientation：表示IMU的当前方向，使用四元数表示

  ​ float64 x，float64 y，float64 z，float64 w

  （3）Orientation Covariance

  ​ float64[9] orientation_covariance：标识方向的协方差矩阵，通常是3x3的矩阵，按行主序排列。它表示对方向估计的信息：

  ​ 对角线上的元素表示各个方向的方差

  ​ 非对角线元素表示方向之间的协方差

  （4）Angular Velocity

  ​ geometry_msgs/Vector3 angular_velocity：表示IMU的角速度

  ​ float64 x，float64 y，float64 z

  （5）Angular Velocity Covariance

  ​ float64[9] angular_velocity_covariance：表示角速度的协方差矩阵，类似于方向协方差，表示对角速度估计的信息

  （6）Linear Acceleration

  ​ geometry_msgs/Vector3 linear_acceleration：标识IMU的线性加速度

  ​ float64 x，float64 y，float64 z

  （7）Linear Acceleration Covarance

  ​ float64[9] linear_acceleration_covariance：表示线性加速度的协方差矩阵，标识对加速度估计的信息

    里程计的坐标发布

    1.fast_lio发布里程计的数据，然后用一个功能包接收odometry话题的数据

    2.我只需要获取目标点位的数据和初始点位的数据（上层），下层的事情不需要考虑（pid算法等会自己调节），雷达的功能就是实时得到点位数据

    3.雷达里程计原理 雷达里程计的目标是通过激光雷达的连续帧数据，计算机器人相对于初始位置的实时位姿，本质是”帧间匹配“与”位姿积累“

    • 数据预处理，激光雷达输出的原始点云需经过滤波，减少后续计算量
    • 帧间匹配：将当前帧点云与上一帧点云（或局部地图）进行匹配
    • 位姿积累：将每帧计算出的相对位姿（相对于上一帧）叠加到初始位姿上，得到机器人相对于世界坐标系的绝对位姿，即里程计数据（nav_msgs/msg/Odometry）

    4.里程计的误差不会很大（1cm）左右

    世界坐标系（右手法则）

    1.世界坐标系是一种笛卡尔坐标系

    2.x是前后运动，y是左右运动，z是上下运动，RX是姿态绕x轴旋转，RY是姿态绕y轴旋转，RZ是姿态绕z轴旋转（livox_mid360的roll，pitch，yaw则分别是绕x运动，顺时针翻滚是正方向。绕y运动，朝下俯瞰是正方向。绕z运动，朝左转是正方向）

    3.激光雷达标定

    • 激光雷达标定是只确定激光雷达传感器内部参数（内参）和相对于其他传感器和世界坐标系的位姿参数（外参）的过程
    • （1）激光雷达坐标系（2）世界坐标系：固定的全局坐标系（3）其他传感器坐标系
    • 世界坐标系以激光雷达启动时的初始位姿为原点

    重定位

    1.雷达在此处位置信息失效、偏移或环境变化后，通过重新采集环境特征、匹配参考数据或融合多源信息，恢复/矫正雷达空间位置与姿态，确保其探测数据（如目标距离、方位）能精准对应真实地理坐标

    2.（1）基于“外部参考信号”的重定位（依赖外部系统，精度高）

    • 雷达实时接收外部参考信息 -> 对比自身当前位置/姿态数据 -> 计算偏差值 ->自动校正雷达探测坐标（如将“雷达相对坐标”转换为“地理坐标系”时的参数修正

    （2）基于“环境特征匹配”的重定位

    • 雷达扫描周围环境，提取特征 ->将提取的特征与预存的“环境参考地图”（如包含梭鱼固定目标位置的数据库）进行匹配 -> 通过匹配的结果反推雷达当前位置 -> 用反推的位置校正雷达后续探测数据

    （3）基于“多雷达协同”的重定位

    • 位置已知的“主雷达”向周围发送自身位置信号，并探测其他“从雷达”的位置 -> “从雷达”同时探测“主雷达”的位置，形成“双向探测数据” -> 通过多组雷达间的距离、方位角数据，建立协同定位模型，计算出“从雷达”的准确位置

    3.雷达里程计有缺陷（1）累积误差（2）绝对位置缺陷。雷达里程计的本质是“相对位移传感器”，而重定位是“绝对位置传感器”，重定位可作为“备用位置源“，帮助李成绩恢复工作或直接替代其输出位置

    4.单只用一个里程计是没有办法进行重定位的，必须结合预先建好的地图

    定位工程实战：从 Livox 点云到机器人位姿（补充）

    1. 理清输入、输出与坐标系

    Livox Mid-360 本身负责测量点云和提供惯性数据，不会凭空输出“相对于已知世界地图的绝对位置”。 一般工作链路是：LiDAR + IMU → 时间同步 → 去畸变 → LIO 里程计 → 与先验地图配准/闭环 → 地图坐标系位姿 → Nav2 导航。

    消息/坐标 含义 常见检查命令
    /livox/lidar Mid-360 原始点云；当前配置可能为 CustomMsg ros2 topic info /livox/lidar -v
    /livox/imu 线加速度、角速度等 ros2 topic echo /livox/imu --once
    /Odometry LIO 估计的位姿、速度等 ros2 topic echo /Odometry --once
    camera_init → body 一些 FAST-LIO 工程使用的里程计位姿链 ros2 run tf2_ros tf2_echo camera_init body
    map → odom 定位修正/桥接通常涉及的地图与里程计关系 ros2 run tf2_ros tf2_echo map odom

    注意：topic 名称大小写敏感；map → odom → camera_init → body → base_footprint 只是某一套桥接拓扑示意。启动前以 ros2 run tf2_tools view_frames、ros2 topic list -t 的实际结果为准，不应在不确定 TF 发布源的情况下重复发布 map → odom。

    2. 为什么需要 TF？如何计算一点在地图中的坐标？

    对于雷达点 \(p_L=(x_L,y_L,z_L)\)，已知雷达到机器人本体的外参 \(T_{BL}\)、机器人本体到地图的变换 \(T_{MB}\)：

    \[ \begin{bmatrix}p_M\\1\end{bmatrix} =T_{MB}T_{BL}\begin{bmatrix}p_L\\1\end{bmatrix} \]

    \(T\) 为 \(4\times4\) 齐次变换矩阵，左上角是旋转矩阵 \(R\)，右上角是平移向量 \(t\)。乘法顺序很重要：先从雷达到本体，再从本体到地图。ROS 2 的 TF API 可以直接处理这类变换，避免手工反复计算。

    查看 TF 和激光数据的实际频率：

    source /opt/ros/humble/setup.bash
ros2 topic list -t
ros2 topic hz /livox/lidar
ros2 topic hz /livox/imu
ros2 topic echo /Odometry --once
ros2 run tf2_ros tf2_echo map base_footprint
ros2 run tf2_tools view_frames

    如果 tf2_echo 报坐标系不存在，先核对 frame_id、发布时间和链路完整性。不能把没有发布的 base_link 直接当成 body。

    3. ROS 2 Python：订阅里程计并转换为二维坐标、航向角

    下面的完整示例使用 /Odometry，输出位置、速度和 yaw。保存为 ROS 2 Python 功能包里的 odom_monitor.py，在已经 source 工作空间的 Humble 环境里运行。Odometry.pose.pose 的坐标含义由消息中的 header.frame_id 决定，不是无条件的地图绝对坐标。

    import math
import rclpy
from rclpy.node import Node
from nav_msgs.msg import Odometry

class OdomMonitor(Node):
    def __init__(self):
        super().__init__('odom_monitor')
        self.sub = self.create_subscription(
            Odometry, '/Odometry', self.on_odom, 10)

    def on_odom(self, msg):
        p = msg.pose.pose.position
        q = msg.pose.pose.orientation
        # 四元数转换为 yaw，适用于观察平面航向角
        siny = 2.0 * (q.w * q.z + q.x * q.y)
        cosy = 1.0 - 2.0 * (q.y * q.y + q.z * q.z)
        yaw = math.atan2(siny, cosy)
        speed = math.hypot(msg.twist.twist.linear.x,
                           msg.twist.twist.linear.y)
        self.get_logger().info(
            f'frame={msg.header.frame_id}, child={msg.child_frame_id}, '
            f'x={p.x:.3f}m y={p.y:.3f}m z={p.z:.3f}m '
            f'yaw={math.degrees(yaw):.2f}deg speed_xy={speed:.3f}m/s')

def main():
    rclpy.init()
    node = OdomMonitor()
    try:
        rclpy.spin(node)
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()

    编译/运行思路：若已有 ament_python 包，把上述文件放到对应 Python 模块目录，在 setup.py 的 console_scripts 注册 odom_monitor = 包名.odom_monitor:main，然后在工作空间执行 colcon build --packages-select 包名 和 source install/setup.bash，最后 ros2 run 包名 odom_monitor。

    分析：这段代码只读取里程计，不执行配准也不做重定位。FAST-LIO 的坐标可能是初始雷达/惯导系，在没有定位器前不要直接声称是 map 坐标。

    4. ROS 2 Python：读取 map 到机器人坐标系的 TF

    下面示例每秒查询一次 TF，打印机器人在 map 中的位置（含错误处理）。保存为 tf_pose_monitor.py 并以相同方式注册到 ROS 2 Python 功能包。

    import rclpy
from rclpy.node import Node
from rclpy.time import Time
from tf2_ros import Buffer, TransformListener, TransformException

class TFPoseMonitor(Node):
    def __init__(self):
        super().__init__('tf_pose_monitor')
        self.target_frame = 'map'
        self.source_frame = 'base_footprint'
        self.buffer = Buffer()
        self.listener = TransformListener(self.buffer, self)
        self.timer = self.create_timer(1.0, self.tick)

    def tick(self):
        try:
            transform = self.buffer.lookup_transform(
                self.target_frame, self.source_frame, Time())
        except TransformException as exc:
            self.get_logger().warn(f'TF 暂不可用: {exc}')
            return
        t = transform.transform.translation
        self.get_logger().info(
            f'{self.source_frame} in {self.target_frame}: '
            f'x={t.x:.3f} y={t.y:.3f} z={t.z:.3f}')

def main():
    rclpy.init()
    node = TFPoseMonitor()
    try:
        rclpy.spin(node)
    finally:
        node.destroy_node()
        rclpy.shutdown()

if __name__ == '__main__':
    main()

    lookup_transform(target_frame, source_frame, time) 的调用顺序不能反。Time() 表示获取最新可用变换；收到时间戳严格的传感器数据时，应查相应时刻的变换并考虑超时，不能只靠“最新”来解决时间同步问题。ROS 2 Humble tf2 Python 教程。

    5. FAST-LIO 的处理链与参数排查

    原笔记已经列出 sync_packages、IMU 去畸变、迭代状态估计、map_incremental() 等步骤，可以把它理解为：

    1. 用每个点的时间偏移与 IMU 数据进行同步。时间戳如果发生乱序，去畸变结果会变差。
    2. 将同一帧不同扫描时刻采样的点变换到统一参考时刻，进行运动畸变补偿。
    3. 将当前帧点云与局部地图做匹配，迭代更新姿态与位置状态。
    4. 将更新的点云融合到局部地图，发布里程计和可视化点云。

    示例检查（运行中，不直接修改参数）：

    ros2 param list /fastlio_mapping
ros2 param get /fastlio_mapping common.lid_topic
ros2 topic hz /cloud_registered
ros2 topic hz /Odometry
ros2 topic echo /Odometry --once

    不同的 FAST-LIO 分支可能使用不同的节点名或参数结构，如果以上命令报“node not found”，以 ros2 node list 与启动日志为准。

    若上坡后高度漂移明显，不要先强行把 Z 设置为零，应依次排查 IMU 与雷达外参、重力方向、时间偏差、缺乏几何约束、局部地图退化与桥接 TF。里程计不能笼统保证 1 cm 精度，误差随环境、运动和标定条件变化；报告中应写明测试基准、里程、评价指标和实测结果。

    6. PCD 到二维 OccupancyGrid 的算法解释

    典型流程为：PCD 点云 → 按高度筛选地面/障碍物 → 体素降采样 → 映射二维网格 → 障碍膨胀 → 保存为 PGM + YAML（或直接发布 nav_msgs/OccupancyGrid）。

    给定点云 \(p=(x,y,z)\)、栅格原点 \((x_0,y_0)\)、分辨率 \(r\)：

    \[ i=\left\lfloor\frac{x-x_0}{r}\right\rfloor,\quad j=\left\lfloor\frac{y-y_0}{r}\right\rfloor \]

    示例：地图原点 \((0,0)\)、分辨率 \(0.05\) m/格时，\((1.20,0.45)\) m 对应索引 \((24,9)\)。将未知区域全部当自由区域是危险的：简单的 PCD 投影仅能可靠标记“有点的位置”，要区分空闲与未知通常还需射线追踪或已知空闲观测证据。

    # 教学示例：用 numpy 将离散障碍点投影为网格索引，不等于完整导航地图生成器
import numpy as np

points_xyz = np.array([[1.20, 0.45, 0.5], [0.10, 0.30, 0.8], [1.18, 0.44, 0.9]])
resolution = 0.05
origin = np.array([0.0, 0.0])
height_min, height_max = 0.3, 1.2
obstacle_points = points_xyz[(points_xyz[:, 2] >= height_min) &
                             (points_xyz[:, 2] <= height_max)]
indices = np.floor((obstacle_points[:, :2] - origin) / resolution).astype(int)
for ix, iy in np.unique(indices, axis=0):
    print('occupied cell:', ix, iy)

    完整 PGM/YAML 地图还必须约定原点、尺寸、世界坐标 y 轴与图像行方向翻转、占据概率/像素映射、未知区域、机器人 footprint 和分辨率。不能直接把点云截图当成可用于 Nav2 的正确栅格地图。

    7. 重定位和里程计不能混为一谈

    • 相对里程计：估计机器人位姿随时间的变化，短期连续但可能累积漂移。
    • 地图定位：利用已知静态地图约束位姿，把漂移中的 odom 轨迹对齐到地图参考系。
    • 重定位：定位中断后，重新估计机器人在地图上的姿态；必须有可匹配的先验信息或外部参考，不是单靠积分里程计恢复绝对位置。

    排查顺序：/livox/lidar 原始数据是否正常 → /livox/imu 是否正常 → /Odometry 是否连续 → TF 是否连通 → 先验 PCD 与实时点云是否同一尺度和坐标约定 → 定位匹配分数/残差是否可信。不要在失去定位时自动将“上一次位置”当成有效的当前位置。

    8. 常见命令问题与修正

    原笔记中 LD_LIBRARY_PATH 的示例存在多余空格，正确写法是：

    # 临时追加动态库搜索路径（等号两侧不能有空格）
export LD_LIBRARY_PATH="/usr/local/lib:${LD_LIBRARY_PATH:-}"

# 确认库的实际路径以及依赖
find /usr/local/lib -name 'liblivox_lidar_sdk_shared.so*' -print
ldd /path/to/your/ros2_node | grep -E 'livox|not found'

    如果动态库不在 /usr/local/lib，需要替换为正确路径；系统服务应优先通过 ldconfig 或 systemd Environment= 正式配置，而不是依赖交互式 ~/.bashrc。

    推荐进一步实验：分别记录水平地面、上坡、台阶、闭环回到原位 4 个场景的平移误差、yaw 误差、Z 漂移、匹配状态与点云帧率，再考虑调整 FAST-LIO 的体素滤波、IMU 参数或 TF 桥接，避免仅凭肉眼看点云判断定位精度。
